# Settings profile save native (step S4, first part)

The worker saves the Settings > Profile form (`save_profile`): the account email, display name, bio, profile fields with their rel=me checks, avatar and header URLs, every checkbox, the reply and quote policies, the forum signature and the profile badges. PHP keeps the session, CSRF, the avatar and header uploads, the cache and export work after a save (`ap_profile_after_save`), the follower Update, the Bluesky profile sync and the notice.

Open to every active account, never admin-gated. Default off. It needs `VAAK_ADMIN_READ_NATIVE=1` and `VAAK_ADMIN_READ_SECRET` plus `VAAK_SETTINGS_PROFILE_SAVE_NATIVE=1`, in both `www.conf` and `vaak.env`. With the switch off in either place PHP saves as before.

## What it does

The `save_profile` action stores uploads first, then builds the same field array it always passed to `ap_profile_save` (checkbox `!empty` semantics, `anti_ai_marker` forced off, `trending_enabled` from the current value when the form omits it) and hands it with the trimmed email to `ap_settings_profile_save_native`. The bridge refuses field shapes the form never sends, posts to `/internal/settings/profile-save` with the loopback token and waits up to 60 seconds, since rel=me checks fetch each linked page.

The worker requires that the owner id is an active account whose `actor_key` is the one PHP sent, then copies:

- `ap_auth_user_set_email`: empty clears the email; otherwise the address must pass `FILTER_VALIDATE_EMAIL` and be at most 200 bytes, and no other active account may use it (case-insensitive). A unique-index clash with a disabled account answers "Could not save email." like PHP. As in PHP the email is saved before the profile, so a profile error still keeps the new email.
- `ap_profile_save_unlocked` validation and sanitizing: name, bio (plain text into paragraphs, or `strip_tags` with the same allow list, the `<a>` rewrite to https-only `rel="nofollow noopener noreferrer"` links and `ap_profile_normalize_summary_html`), forum signature, up to eight fields (URL coercion, `rel="me"` links, `strip_tags(…, '<a>')`, escaping), avatar and header URL checks, the existing reply and quote policy when the form sends an unknown one, and badges filtered to the selectable catalog with Admin and Supporter taken from account authority.
- `ap_profile_verify_attachments`: each field URL is fetched through the guarded, pinned link preview transport (5 seconds, 512 KiB, the same redirect and circuit rules), the page is scanned for `<a>`/`<link>` with `rel` containing `me` and an absolute https href naming one of the six identity URLs, and a link that does not name one gets one HEAD whose Location is checked (PHP's HEAD is unpinned; this one is pinned to the checked addresses). A verified field gets `verified_at` as PHP writes it.
- The write: a transaction holding `pg_advisory_xact_lock(hashtext('vaak:profile-save:' || key))`, the same key as PHP's session lock, so the two saves never interleave; the existing algorithm, trending and downranking switches are read under it, then the same upsert with `json_encode` slashes and Unicode unescaped (U+2028/2029 escaped).

The reply is `{protocol_version, ok, error, email_saved, trends_changed, algorithm_changed, request_binding}`. The bridge rejects any other key, a binding for another account, an error on success, a success without the email saved and a failure that reports changes. On success PHP runs `ap_profile_after_save` (profile cache delete, trends epoch, timeline invalidation, homepage export, public document invalidation) with the two change flags, then its follower Update and Bluesky sync as before.

Saves in PHP instead (the worker answers 422 before any write, except that the email may already be set to the same value) when: text matches the `ap_fix_utf8` mojibake pattern, an email is outside the dot-atom shape proven against `filter_var`, a field holds a named HTML entity other than `&amp; &lt; &gt; &quot; &apos;` or an unusual numeric one, a URL has a port, user info, brackets, control bytes or an empty host, an avatar or header host is an IP literal, a rel=me page has an href PHP would decode differently, the rel=me checks run past 45 seconds, the account has no stored profile row yet, or the account is disabled or not the signed-in one.

## Parity check

`api/bin/settings-profile-save-native-review.php` (sandbox only) has two modes.

`--corpus OUT.json` runs genuine `strip_tags`, `filter_var` and the ap-db.php helpers over hand-picked and generated inputs; `cargo test -p vaak-worker actual_php_helper_corpus -- --ignored` (with `PROFILE_SAVE_CORPUS=OUT.json`) compares the Rust copies byte for byte. 2026-10-21: 394952 of 404266 answers compared with `CORPUS_N=80000` (the rest are the documented fallbacks), all equal.

The fixture mode seeds `ap_users`, `actor_profile` and `ap_supporter_codes`, runs the genuine `ap_auth_user_set_email` then `ap_profile_save` path, reseeds, runs the native save against a running worker and compares results, after-save flags and the full rows. Scenarios cover plain, HTML and Mastodon-style bios, every validation error, signature checks, media URLs, fields with URLs, anchors, text, entities and skipped rows, forged and capped badges, admin and supporter authority, policy fallback, trend and algorithm changes, all checkboxes, email clear, taken, disabled-account clash, email-before-profile ordering, and fallbacks that must leave the rows untouched. Fixture field hosts are `.invalid`, so neither side verifies a page there; the rel=me scan is covered by the corpus.

2026-10-21: 44/44 checks with INTEGER ids and 44/44 with BIGINT ids.
