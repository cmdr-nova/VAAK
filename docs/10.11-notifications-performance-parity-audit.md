## Current native path and costs

The Notifications partial first releases its PHP session lock. Its empty soft-navigation shell avoids hydration and mark-read; the async fill tries `/shadow/mentions-html` with a 1,500 ms total budget, then the PHP grouped renderer. The latter may try the JSON notification bridge with a 350 ms budget, followed by PHP Redis/projection/hydration recovery. Under database contention, the native HTML attempt can consume its budget before PHP executes much of the same work. Existing stage headers distinguish fetch, prefetch, render and total; an authenticated production capture of those stages is still needed to attribute the reported delay.

`notif_list.rs::notifications_shadow_resolved` probes an exact owner/limit/type/cursor cache key, then alternative warm heads. Each cache hit calls `audience::filter_notifications` before the caller knows whether that head can fill the page. Candidate head hits can therefore repeat fresh account, moderation and audience SQL before ultimately missing and falling back. Do not reuse a filtered authorization decision across requests or awaited enrichment to reduce this cost. A future bounded raw-envelope selection boundary could select the usable head first, then enforce the complete current-policy grant once, but must preserve filtered-head/cursor behavior before replacement.

`mentions_html.rs::mentions_html_fill` additionally loads the viewer actor, following relationships, moderation, interaction flags and Ask/Bluesky facets, and writes nested Redis fragments individually while painting. These operations use multiple database connections and awaited enrichment. Notifications current-audience lookup shares the normalized quote-alias event query identified in the navigation audit, so the separately reviewed expression-index optimization may help this path. No Rust query count or production speedup was measured in this phase; repeated calls identified in source are not timing evidence.

## Exact remaining parity gates

- The native list warmer still spawns `api/bin/notif-projection-fill.php` when projection coverage is thin. Native projection materialization is not native entity hydration.
- The PHP first All page merges Phyrian notifications after obtaining a nonempty primary list. The Rust Mentions HTML fill does not call that PHP producer. Full Phyrian offer/type/action equivalence is unproved.
- PHP page cursors and has-more are calculated from the unfiltered selected rows before hiding notifier accounts. Rust warm list filtering occurs before its truncation, cursor and has-more calculations. Current hidden-row windows and all-hidden terminal pages need actual caller/reference tests; changing these contracts as a performance shortcut would be unsafe.
- PHP cold grouped rendering can complete boundary groups through lookahead; warm-list behavior intentionally skips lookahead. Native grouping needs complete actual PHP caller comparisons, including twin identities, raw/source cursor consumption and filter changes.
- Complete notification actions, read-watermark behavior, current Settings/privacy trees, disabled identity, root versus embedded moderation, dynamic quotes/polls/Ask, first-request effects and cold/older-page fallback need end-to-end parity evidence. The lean Rust painter alone is not full PHP-equivalent Notifications.
- Fresh authorization after awaited enrichment, and policy/source withdrawal at final publication, need explicit race tests. No broad security conclusion follows from this source audit.

The practical accepted improvement here is the narrow malformed empty-list recovery repair. Further native Notifications migration requires the gates above; no activation, commit or deployment was performed by this phase.
