# Rust fan-out delivery (cutover D2)

`rust/vaak-worker/src/fanout_delivery.rs` works `ap_fanout_delivery_queue`, the durable per-inbox queue that `ap_deliver_durable` fills for posts, boosts, likes and other fan-out. It replaces `api/ap-fanout-delivery-worker.php` and keeps its rules:

- Leases older than 600 s go back to pending with `attempts + 1` and "Worker lease expired".
- Rows are claimed one at a time with the `status = 'pending'` guard, so PHP and Rust never both send one row.
- A Bluesky activity bound for a non-Bluesky inbox fails with "Bluesky activity is not delivered".
- Suspended hosts (`ap_fanout_host_health`, VAAK_FANOUT_DEAD_DAYS / VAAK_FANOUT_DEAD_FAILURES) fail without a request, except the daily probe. The probe is re-queued the way `ap_fanout_host_requeue_probe` does.
- A host circuit opens for 300 s after 3 failures in a row. It is kept in memory.
- Success, retry delay (`min(3600, 15 * 2^(attempts-1))`, or the open circuit), the 12-attempt limit, the 1-attempt limit for a suspended host's probe, and the host-health writes follow `ap_fanout_worker_outcome`, `ap_fanout_host_note_success` and `ap_fanout_host_note_terminal`.
- Error text keeps PHP's shape (`HTTP 403 …`, `No HTTP response from inbox …`), because it decides whether a host counts as dead.

The request matches `ap_deliver_signed_json`: `ap_as2_pleroma_document($activity, false)` (`ap_public_doc::pleroma_document_with`), a draft-cavage rsa-sha256 signature over `(request-target) host date digest` from `ap_sign.rs`, HTTP/1.1, IPv4 only, connected to addresses that all passed the public-address check, no redirects, 2.5 s. Keys come from each row's `priv_path`, as PHP reads them.

Hosts run in parallel (8 at a time), one row at a time per host.

## Switch

- `VAAK_FANOUT_DELIVERY_RUST=1` in `/etc/mkultra/vaak.env` starts it inside `vaak-worker serve` (vaak-worker-shadow-http). No new unit.
- While it runs it sets `vaak:fanout_delivery:rust:v1` (cache Redis, 30 s TTL) every pass. `ap_fanout_rust_worker_active()` sees it, and PHP stops starting `ap-fanout-delivery-worker.php` (the enqueue kick, `ap_fanout_host_kick_worker`, and the Redis wake worker). When the heartbeat is missing or stale, PHP starts its worker again.
- Rollback: remove the line and restart the worker. PHP picks the queue back up within 30 s.

## Watching it

- `HGETALL vaak:fanout_delivery_rust:stats:v1`: claimed, succeeded, retried, failed.
- Journal lines `fanout_delivery claimed=… succeeded=…` per busy pass.
- `VAAK_AP_DELIVERY_LOG=/path/ap-delivery.log` makes failures and Follow/Accept/Reject go to the same log PHP writes (lines end in `via=rust`); unset, they go to the journal.

## Inline sends (cutover D3)

PHP still sends a few deliveries itself before it queues the rest:

- `ap_deliver_public_activity`: Bridgy Fed (5 s, first 2xx wins) and the first 6 followers, reply targets and mentions
- `ap_deliver_followers_activity`: the first 8 followers
- `ap_deliver_inline_then_queue` (profile Update and Move): the first 50 inboxes

With `VAAK_FANOUT_SYNC_RUST=1` next to `VAAK_FANOUT_DELIVERY_RUST=1` in `/etc/mkultra/vaak.env`, the worker also keeps `vaak:fanout_delivery:rust_sync:v1` fresh (same 30 s TTL). `ap_fanout_rust_sync_active()` sees it, and PHP queues those deliveries instead of sending them: Bridgy, the first followers and reply/mention targets at priority 5, so they are claimed before bulk rows (10/20/50), and profile Updates and Moves with their normal priority. Every POST then leaves from Rust. If the queue insert fails, PHP sends them inline as before.

Bridgy rows get the 5 s timeout PHP gave them; every other host keeps 2.5 s. One host sends at most 4 rows per pass, so a slow host cannot hold the pass (and the reply queued behind it) for 40 x 2.5 s. The rest of that host's rows wait for the next pass.

What changes for senders: an idle worker waits on PHP's `vaak:queue:fanout-delivery` wake-up push (queue Redis) instead of sleeping, so a queued row is picked up at once; without Redis it polls every 2 s. A pass that hits the per-host cap runs the next pass straight away. Only the first Bridgy inbox (the personal one) is queued, matching the inline loop that stopped at the first 2xx; a failure is retried on that row instead of falling over to the shared inbox.

- On: add `VAAK_FANOUT_SYNC_RUST=1`, restart vaak-worker-shadow-http.
- Off: remove it and restart. The worker deletes the key at start, so PHP sends inline again at once (within PHP's 5 s cache).
- Watch: `publish_status ... delivered=0 queued=N` in ap-inbox.log, and `succeeded` keeps pace with `claimed` in the stats.
- Tests: `api/bin/fanout-sync-rust-smoke.php` and `api/bin/move-fanout-cap-smoke.php` (standalone), and the sync heartbeat check in `fanout-rust-delivery-smoke.php`.

## Your likes and unboosts (cutover A1)

With `VAAK_FANOUT_ACTIONS_RUST=1` the worker also sets `vaak:fanout_delivery:rust_actions:v1` (cache Redis, 30 s TTL), and `ap_fanout_rust_actions_active()` reads it. While it is fresh, the action queue's likes, unlikes and unboosts send nothing themselves: `ap_deliver_action_via_rust()` queues their inboxes at priority 3, ahead of D3's priority 5. An unboost queues Bridgy and the author at priority 3 and its followers at the normal bulk priority. A boost already goes through `ap_deliver_public_activity()`, so D3 covers it.

The action now reports ok once queued; the queue retries a failed inbox up to 12 times. When the key is stale or the insert fails, PHP sends inline as before.

- On: add `VAAK_FANOUT_ACTIONS_RUST=1`, restart vaak-worker-shadow-http. Off: remove it and restart.
- Watch: `like_queued_rust`, `unlike_queued_rust`, `unboost_queued_rust` in ap-inbox.log, and priority 3 rows in the queue.
- Left in PHP: follow and unfollow (personal inbox, then shared fallback), bites, and Bluesky actions.
- Tests: `api/bin/fanout-actions-rust-smoke.php` (standalone).

## Not moved

`ap_publish_delivery_queue` (`ap-publish-delivery-worker.php`) stays PHP. It decides who gets a post (reply and quote addressing, mention inboxes, quote authorization requests) and runs the Bluesky crosspost; with D3 on, it only queues the Fediverse sends.

## Tests

- Unit tests in `fanout_delivery.rs` for host normalising, live/dead error classes, outcomes, delays, suspension and terminal updates.
- `api/bin/fanout-rust-delivery-smoke.php` in the CI database smokes: unresolvable host, Bluesky guard, suspended host, failed probe, expired lease, heartbeat and stats. Nothing it queues resolves, so no request leaves CI.
