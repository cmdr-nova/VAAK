# Paid Clearance Supporter rewards and registration applications: review phase

Registration remains closed. This is an uncommitted implementation and isolated fixture phase, not authorization to activate public registration. No production billing, accounts, messages, database changes, deployment, or badges were created.

## Behavior

With registration approvals enabled, every registration request creates a pending application, including paid supporters. Neither a legacy invite nor payment bypasses approval. The existing invite field becomes an optional Supporter code; email remains optional when no code is supplied. A code requires the same email used for paid Clearance. Approved applications consume the reward and create the account and earned badge in one transaction; rejection frees its reservation without spending it. Current paid users can redeem in Settings without receiving administrative privileges.

Codes are separate from legacy invite codes, hashed in VAAK, single-use, and bound to normalized payment email. The trusted in-process issuer records hashes of the customer and settled receipt. It has no public HTTP issuance endpoint. Only the Clearance server selects payment proof; user-controlled notes, membership status, cached badge JSON, and freely selected flair have no reward authority. Current members receive no automatic badges.

Supporter is derived from a current consumed server-owned grant joined to the profile subject's active account. PHP and Rust preserve six ordinary flair slots plus the earned badge, including malformed/padded/late badge input and warmed caches that omit an earned badge. PostgreSQL Settings saves and reward awards use the same actor advisory lock. Withdrawal or subject disablement invalidates Rust header admission even when another user views that subject.

## Clearance payment source and staging

The original website sources remain unchanged. Reviewable staged copies, a unified patch, and original/staged hashes are in `rust/target/parity-evidence/supporter-registration-phase/clearance-supporter.patch` and `clearance-manifest.json`. Website deployment must remain separate from VAAK, exclude configuration/data/internal documentation, and verify both original and live baseline before applying this patch.

The existing subscription Checkout emits trusted `metadata.type=monthly_subscription`; generic one-time donation Checkout emits `one_time_donation` and does not grant Clearance. Initial reward issuance requires the same customer's complete, paid, live subscription Checkout, plus a captured positive settled live charge linked to its paid invoice and exact subscription/customer/charge. Customer-only membership, trials, unrelated purchases, legacy codes, zero payments, failed/uncaptured/disputed or fully refunded initial receipts do not qualify. Partial refunds retaining a positive captured payment qualify. Existing permanent Clearance/OpenSim/Discord access is unchanged, including after subscription cancellation.

Read-only Checkout/Charge/Invoice GETs share a four-second total transport budget and a maximum five pages each for Checkout and charges. Failure or insufficient historical proof fails closed. Negative and failed attempts persist a 15-minute admission timestamp before I/O; the conditional update prevents concurrent initial lookups. Issued rewards require no repeat Stripe calls on navigation. Transport fixtures explicitly declare all Stripe objects; no live Stripe integration was verified. Fields checked against official Stripe references at the integration's existing 2024-06-20 version: [Checkout Session](https://docs.stripe.com/api/checkout/sessions/object?api-version=2024-06-20), [Charge](https://docs.stripe.com/api/charges/object?api-version=2024-06-20), [Invoice](https://docs.stripe.com/api/invoices/object?api-version=2024-06-20).

Code derivation requires a stable private `VAAK_SUPPORTER_CODE_SECRET` of at least 32 characters. Changing it while preserving existing issuance rows fails closed rather than minting replacements; retain and back up the original secret, and review an explicit migration before rotating it. Payment-email changes similarly require an explicit reviewed reconciliation. Later refunds/chargebacks do not silently change permanent access or retroactively revoke existing rewards; that policy remains unresolved rather than invented here.
