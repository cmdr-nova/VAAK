# Admin invites and registration switch native (step A10e)

The worker runs `invite_create` and the registration switch, `registration_open` and `registration_close`. PHP keeps the session, CSRF, the admin-only gate, the notice and error text, and the page. Approving or rejecting an application (`registration_approve`, `registration_reject`) stays PHP: it provisions the account (keys, profile) and sends the approval mail through a separate process. It uses the `/internal/admin/action` route, bridge and reply from A10a (`10.21-admin-downranking-actions-native.md`).

Admin only. Default off. It needs `VAAK_ADMIN_READ_NATIVE=1` and `VAAK_ADMIN_READ_SECRET` plus `VAAK_ADMIN_INVITES_ACTIONS_NATIVE=1`, in both `www.conf` and `vaak.env`. Other families' switches do not open this one.

## What it does

- invite: copied from `ap_auth_invite_create` as the Invites form calls it. The note is trimmed, cut to 200 characters and stored as NULL when empty; the code is eight and four upper-case hex digits from the operating system's random source, as PHP's `random_bytes`; `created_by` is the acting admin and there is no expiry. It runs in a transaction that first reads the acting account `FOR SHARE` (an active admin with the actor key PHP sent). The reply carries the new code, which the bridge accepts only in that exact shape, and PHP shows "Invite created: CODE".
- registration switch: copied from `ap_registration_set_accepting`, in PHP's lock order: `LOCK TABLE ap_users, ap_registration_applications IN SHARE ROW EXCLUSIVE MODE`, then the admin row `FOR UPDATE` with `is_admin = 1` exactly, then the control row update. A missing control row answers "Could not change registration. Check registration control readiness."; otherwise PHP shows its reopened or closed notice, which still depends on `VAAK_REGISTRATION_APPROVALS` on the PHP side.

Outcomes: `invite_created`, `registration_opened`, `registration_closed`, `registration_not_ready`.

Runs in PHP instead (the worker answers 422 before any write) when the note holds a NUL, `ap_registration_control` is missing or the applications table lacks `supporter_hash` (PHP's `ap_registration_approvals_schema` creates or alters it, and that DDL stays in PHP), the account's admin flag is anything but 1 for the switch, the acting account is not an active admin with that actor key, a random code collides with an existing one, or any query fails.

## Parity check

`api/bin/admin-invites-actions-native-review.php` (sandbox only) runs the genuine handlers from `ap-admin.php` with the genuine `ap_auth_invite_create`, `ap_registration_set_accepting` and its helpers against a seeded PostgreSQL fixture. For each scenario it runs PHP with the switch off, reseeds, runs the native branch with PHP's handlers disabled, and compares the notice, error, view, every invite row (the random code checked for its shape), the registration control row and the applications table's columns. It also checks the fallbacks write nothing and the bridge validator. Run the worker with `VAAK_ADMIN_INVITES_ACTIONS_NATIVE=1`.

Scenarios cover invites with a padded, missing, blank, 250 character, HTML and emoji note, opening and closing registration with approvals off and on, an empty control table, a missing control table, an applications table without its supporter column, an admin flag of 2 and a disabled admin.
