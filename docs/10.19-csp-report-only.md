# Content-Security-Policy (report-only)

VAAK's HTML entry points send a Content-Security-Policy in **report-only**
mode. Browsers load everything as before and POST a report for every load the
policy would have blocked. Read the reports for a while, fix or allow what is
real, then turn enforcement on.

The policy and the report handler live in `api/ap-csp.php`.

## Where the headers go

`ap_csp_send_headers('app')` runs in:

- `vaak/index.php` (login, registration, and the signed-in shell it boots)
- `api/ap-admin.php`
- `api/ap-user.php` and `api/ap-cmdr-nova.php` (profiles, `/users/…`, `/@…`)
- `api/ap-actor.php` (instance actor HTML)
- `api/ap-instance-docs.php` and `api/ap-public-policy.php` (privacy, conduct)

`/oauth/authorize` (`ap_masto_oauth_authorize`) uses `ap_csp_send_headers('oauth')`.

`api/ap-oembed.php?format=html` is left out on purpose. Other sites embed it.

## The OAuth authorize page

The authorize page shows a password form. If another site could frame it, that
site could trick a user into signing in and approving an app (clickjacking).
So this page **enforces** these headers now, in both modes:

```
Content-Security-Policy: frame-ancestors 'none'; report-uri /vaak/?csp_report=1; report-to vaak-csp
X-Frame-Options: DENY
```

It also gets the report-only page policy, with `frame-ancestors 'none'`.

## The policy

| Directive | Value | Why |
| --- | --- | --- |
| `default-src` | `'self'` | |
| `script-src` | `'self' 'unsafe-inline' https://cdn.jsdelivr.net` | Inline `<script>` blocks and `on…=` handlers are everywhere. jsDelivr serves qrcode-generator (2FA setup). |
| `style-src` | `'self' 'unsafe-inline' https://cdn.jsdelivr.net` | Inline `<style>` and `style=` attributes. Phosphor icon CSS comes from jsDelivr. |
| `font-src` | `'self' data: https://cdn.jsdelivr.net` | Phosphor icon fonts. |
| `img-src` | `'self' data: blob: https:` | Remote avatars, headers, attachments and link previews come from any fediverse host, the R2 media CDN, and `cdn.bsky.app`. |
| `media-src` | `'self' data: blob: https:` | Remote video and audio, including `video.bsky.app`. |
| `connect-src` | `'self' https:` | Same-origin fetch and SSE. hls.js also fetches playlists and segments from remote video hosts. |
| `frame-src` | `'self' https://www.youtube-nocookie.com https://www.youtube.com` | Click-to-play YouTube embeds. |
| `worker-src` | `'self' blob:` | `/vaak/sw.js`, and hls.js's blob: worker. |
| `manifest-src` | `'self'` | |
| `object-src` | `'none'` | |
| `base-uri` | `'self'` | The shell sets `<base href="/vaak/">`. |
| `form-action` | `'self' https:` | The authorize form redirects to the client's https `redirect_uri`. |
| `frame-ancestors` | `'self'` (`'none'` on authorize) | Matches the `X-Frame-Options: SAMEORIGIN` the entry points already send. |

Reports go to `report-uri /vaak/?csp_report=1`, which Firefox and Safari use.
Chrome uses the Reporting API instead. It reads `report-to vaak-csp`, which
points at the `Reporting-Endpoints` header. That header is only sent over
https, with the request's own host.

Because of `'unsafe-inline'`, this policy cannot catch injected inline script.
It catches script, style, frame and object loads from hosts that should not be
there, plus `<base>` and form hijacks. Getting rid of `'unsafe-inline'` is the
next step (see the end of this page).

## The report endpoint

`POST /vaak/?csp_report=1` is answered early in `vaak/index.php`. That happens
before the session, CSRF checks, or the database load. The response is always
`204` (or `405` for anything other than POST).

- Bodies over 64 KiB are dropped. At most 10 reports from one body are logged.
- Rate limit: 20 report requests a minute per client and 300 a minute overall,
  counted in Redis. The client is counted by a hash of its address. Without
  Redis, only the overall limit applies, counted in a temp file.
- Only these fields are logged: time, disposition, directive, blocked URL,
  document URL, source file, line. URLs are cut down to
  `scheme://host[:port]/path`, so query strings and fragments (OAuth codes,
  search terms, tokens) are never written. `data:`, `blob:` and extension URLs
  keep only their scheme. Script samples, IP addresses and user agents are not
  logged.

The log is `/var/log/mkultra/ap-csp.log`. Set `VAAK_CSP_REPORT_LOG` to use
another path. It rotates once at 1 MiB, to `ap-csp.log.1`.

## Reading the reports

There is one JSON object per line:

```json
{"t":"2026-10-19T09:00:00Z","disposition":"report","directive":"img-src","blocked":"http://old.example/avatar.png","document":"https://vaak.example/vaak/","source":"","line":0}
```

To see what is being blocked, most frequent first:

```sh
jq -r '[.directive, .blocked] | @tsv' /var/log/mkultra/ap-csp.log | sort | uniq -c | sort -rn | head -40
```

To see which pages trigger a given directive:

```sh
jq -r 'select(.directive == "script-src-elem") | [.document, .blocked, .source, .line] | @tsv' /var/log/mkultra/ap-csp.log | sort | uniq -c | sort -rn
```

To see only the last day:

```sh
jq -r --arg since "$(date -u -d '1 day ago' +%FT%TZ)" 'select(.t >= $since) | [.directive, .blocked] | @tsv' /var/log/mkultra/ap-csp.log | sort | uniq -c | sort -rn
```

How to read what comes up:

- **`chrome-extension`, `moz-extension`, `safari-web-extension`** in `blocked`
  or `source`: a browser extension in a viewer's browser. Ignore these.
- **`img-src` / `media-src` with an `http://` URL**: a remote post links
  plain-http media. The browser blocks that as mixed content anyway. Ignore it,
  or upgrade the URL where VAAK builds it.
- **`script-src-elem` / `style-src-elem` from an https host**: something loads a
  script or stylesheet from a host the policy doesn't list. If VAAK loads it on
  purpose, add the host in `ap_csp_policy()`. If not, look into it. This is
  what the policy exists to catch.
- **`frame-src`**: an embed from a host that isn't listed (for example a new
  video provider in link previews). Add it if it is meant to be there.
- **`connect-src` / `worker-src`**: a new fetch or worker target. Same
  question.
- **`frame-ancestors`**: some site tried to frame the page. On the authorize
  page this was blocked (`disposition: enforce`). Note the document, and the
  framing site if you can find it in the access logs.
- **`base-uri` / `object-src` / `form-action`**: these should never show up from
  VAAK's own markup. Treat them as possible injection.

## Turning enforcement on

When a week of reports holds nothing but extension and mixed-content noise:

1. Add `VAAK_CSP_ENFORCE=1` to the PHP-FPM pool environment (for example
   `env[VAAK_CSP_ENFORCE] = 1`), then reload php-fpm.
2. Every page now sends `Content-Security-Policy` with the same policy, and
   reports keep arriving with `disposition: enforce`.
3. To roll back, remove the variable and reload. No deploy is needed.

## Tightening later

- Move inline `<script>` blocks to per-request nonces, and replace the
  `on…=` handlers (about 60 in `ap-admin.php`) with listeners. Then drop
  `'unsafe-inline'` from `script-src`.
- Narrow `img-src` and `media-src` once remote media goes through a VAAK
  proxy or a known CDN.
- Narrow `connect-src` to the video hosts that actually show up in reports.
