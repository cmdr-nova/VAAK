# Current Search component facts checkpoint

Search remains inactive. This stage supplies presentation facts to the pure Search account/tag painter; it does not admit sources, perform remote resolution, authenticate requests, or establish complete Search parity.

`search_components::ComponentContext::load(db, owner, accounts)` binds an active current owner and a maximum 100 server source accounts. The component context is recreated per batch and after durable mutations. It reads the owner's AP following, connected Bluesky graph/cache profiles, requested numeric account mappings/current local IDs, host emoji URLs through fixed set-based queries. Token resolution is synchronous; account-card count does not multiply graph SQL queries. Account tokens have private source/fact fields and read-only getters; tag tokens preserve the canonical collector's `following` snapshot. Neither token deserializes browser facts. Runtime painters accept these tokens. The context is presentation state and must remain downstream of source admission.

Canonical following branches are distinct. UI following uses the rich case-preserving membership map plus the canonical lowercased account-key fallback. Numeric relationship fallback compares canonical CRC IDs and raw following actors through actual account-ID alias rules. The legacy PHP regex in `ap_masto_remote_account_acct_key` and `ap_masto_actor_id_aliases` lacks a slash after `users`: an uncached `/users/Alice` can keep its raw-URI CRC while `/@Alice` uses a lowercased acct CRC. The native resolver preserves this observed behavior. Unicode lowercase uses the previously verified PHP query lowercase helper, including contextual Greek sigma. Numeric local account ID `1` retains the special cmdr_nova branch.

`search-components-php-postgres.php` extracts and executes actual canonical helpers and account/tag painters against the same PostgreSQL tables. Only server-session/PDO and pre-provisioned schema migration IO boundaries are supplied by the fixture; relationship, alias, profile-name, emoji and tag policy helpers remain canonical. Separate PHP processes avoid request-local relationship/profile memo contamination across owners and mutations. The Rust fixture calls the actual module graph and compares complete HTML on INTEGER and BIGINT schemas, including cached/uncached numeric IDs, alias case, connected Bluesky DID/handle follows, local canonical input names/usernames retained across profile/vanity edits, guest username fallback, current emoji URL changes, canonical tag-follow snapshot truthiness. Current owner/input binding, batch limits, disabled owners and explicit fallback branches are also checked.

Unmapped numeric remote IDs requiring remote actor/follower/DM recovery, uncached Bluesky handles requiring identity resolution, and guest numeric relationship contexts remain explicit whole-batch PHP fallback boundaries. Invalid unused Bluesky profile JSON is ignored as canonical cache-get absence; a proven durable DID follow still works. External resolution, migration of missing tables, current status admission, complete profile/account serialization, CSRF response injection, Settings/action dispatch and Search caller/browser integration are separate gates. The retained account source contains unpainted fields unchanged; local display name/username remain incoming snapshot fields; only `acct` follows canonical input username or local-key fallback.
