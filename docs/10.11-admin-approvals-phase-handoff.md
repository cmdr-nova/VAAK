# Admin parity and staged Approvals handoff

This is the next implementation phase after the composer/navigation repair passes fresh review. No registration opening, beta launch, Support Code/Clearance change, deployment or commit is authorized by this phase. Existing invite registration must continue unchanged with the new mode disabled by default.

The user's 10.13 item requests an Approvals page under Admin. Audit the existing eleven Admin pages and their action/view/CSRF gates, then implement the staged approval workflow using the current PHP authentication authority. Keep the distinction between native read-page parity and retained PHP mutations explicit.

Current boundaries: `api/ap-admin.php` has `$vaakAdminOnlyViews`, `$vaakAdminOnlyActions`, session CSRF validation and the Admin navigation. `api/ap-auth.php::ap_auth_register` currently validates and consumes an invite, creates `ap_users` and `actor_profile`, provisions keys, follows/notifies the operator and logs in the new account. Calling it directly from an administrator's approval action would replace the administrator's session with the applicant's session. Account creation must therefore have a shared internal path that does not log in during approval, while preserving the existing invite caller's behavior and effects.

Pending applications must confer no account capability: no login/2FA/OAuth, posting, public profile/actor, publishing or federation. Store only a password hash; expose applicant details only to a currently active administrator. Approval/rejection must re-read current role/disabled state, require CSRF, and transition atomically and idempotently. Handle username/email collisions, concurrent duplicate submissions, replay and invite consumption safely. Do not use ban/unban as the pending state.

Verify actual SQLite and PostgreSQL INTEGER/BIGINT behavior; pending login/OAuth/public actor denial; guest/non-admin/disabled/revoked admin and bad-CSRF denial; duplicate username/email and concurrent/repeated decisions; unchanged invite registration and administrator session preservation. Test actual declarations/controllers where feasible and clearly declare any fixture substitution. Freeze current source and genuine PHP references under ignored `rust/target/parity-evidence/`, then obtain fresh independent verification, anti-pattern and quality review before accepting this phase. Do not count PHP fallback as completed native parity.
