# Navigation backend latency — October 11, 2026

The live 0.8.35 Trending endpoint releases the session at entry, but its renderer immediately calls `ap_auth_current_user()` twice. Each call starts a writable session again. The first reopened session therefore remains locked throughout trend-cache reads and current moderation checks. Another request from the same browser can wait behind the entire sidebar request, including navigation and Notifications.

The narrowly scoped correction closes the session in `finally` immediately after each fresh identity read inside `admin_trends_sidebar_html`. Both identity reads remain; an account switch during cache I/O still suppresses the response. The current block/mute/downrank and word-mute predicates, cache contents and cache ages are unchanged. No HTML authorization result is reused across requests.

`api/bin/trending-session-lock-review.py` executes two real PHP processes against the same isolated file-backed session and actual extracted auth readers/renderer. Schema bootstrap, cookie emission, fixture cache and DB transport are explicitly isolated. Before the correction, a 900 ms cache delay held the consumer for approximately 880 ms and kept the producer's session active. Afterward, the consumer acquired the session in approximately 0.05 ms, retained its stored draft and changed the account; the producer's late fresh identity check suppressed HTML. All seven checks passed. The original test setup initially failed because PHP strict sessions rejected a nonexistent fixed session ID; the fixture now creates its isolated empty session file before seeding. Existing Trending current-policy fixtures passed 120 SQLite/INTEGER/BIGINT cases. This establishes the session contention defect, not the user's exact end-to-end 12-second latency.

## Database observations

Read-only production observations on allowlisted `novalandia-bots` showed four CPUs, load 10.48/10.30/9.70, approximately 4.6 GiB available memory and CPU pressure avg10 86.65%. One sample had 15 active PostgreSQL queries with maximum age seven seconds. A second aggregate sample had nine normalized-object query structures, maximum age 5.17 seconds, and four Bluesky `lower(author_handle)` lookup structures, maximum age 1.49 seconds. No active query literals, identities, post bodies or secrets were retained. Both trend disk caches were present, containing 30 tag candidates and 20 status candidates, approximately 31 minutes old; the current caches were not cold.

A later five-second cgroup sample showed PostgreSQL at 3.24% of one core and the three separate Bluesky feed generators at 18.76%, 20.16% and 14.43%. The workload is bursty; these samples do not prove a sustained CPU allocation or establish a particular browser request's timing.

A nonexecuting production EXPLAIN of the complete unchanged normalized-event denial query estimated cost 4,781,570.84, approximately 186,357 type-index candidates, a correlated full events scan and JIT. No matching normalized-object expression index existed. No production EXPLAIN ANALYZE or load test was run. The raw cache and backend policies are not made less fresh for speed.

## Event index gate

`api/bin/navigation-events-index-review.py` extracts six actual query strings from current `audience.rs` and `home_hydrate_ranked.rs`, preserving their bytes and hashes. It evaluates them before/after `events(rtrim(object_id, '/'), id DESC)` on isolated INTEGER and BIGINT schemas with 23 edge rows and 20,000 unrelated fillers. All 12 exact result vectors match; unordered denial sets are compared as sets, while ordered hydration vectors retain their order. Fixtures cover deletion/tombstones, deleted updates, private orphan Announce, private original plus Announce, explicit/mismatched original actor, self-replies, null actions, content preference, Note/Quote and multiple trailing slashes. Every tested after-plan uses the index. The same predicates and latest-ID ordering remain intact.

Local single-run timings improved, including the alias-denial query from 180.53 ms to 0.65 ms on INTEGER. Timings on this disposable local dataset are not production response measurements. An independent rerun separately passed all 12 vectors. The proposed Bluesky handle expression index remains deferred: unordered LIMIT 1 can choose a different DID when multiple rows share a handle. No feed interval, caps, retention or visibility changes were made.

Explicit root-host maintenance is reviewable in `api/bin/navigation-events-index-maintenance.py`: inspect, create, and confirmed-owned rollback are separate phases. It refuses different definitions, invalid existing indexes, equivalent differently named indexes and excessive resource pressure. Creation is concurrent, with a 10-second lock timeout, at most 30-second statement timeout, 64 MB maintenance work memory, no parallel maintenance workers, a 45-second overall phase budget and client process-group cancellation. A failed/cancelled CREATE may leave an invalid server-side index: inspect separately and only drop a confirmed index created by this maintenance. No blind retry or schema-bootstrap DDL is introduced. The parent coordinator owns review and any production execution.

Evidence is under `rust/target/parity-evidence/navigation-backend-latency/`: exact query vectors/plans, session concurrency and the retained live read-only query/cgroup receipt. Full browser navigation, Notifications and migration readiness remain separate gates; no native renderer activation follows from this index proof.

## Production maintenance receipt

The independently reviewed 2-second-lock maintenance script was executed once after confirming that the index was absent. Its resource gate passed at load 7.10, CPU pressure 63.22% and approximately 4.5 GiB available memory. PostgreSQL canceled concurrent creation on the lock timeout, leaving the exact intended definition invalid and ready. A separate independent catalog inspection confirmed this state. Only that confirmed-owned incomplete index was then dropped concurrently, and a fresh catalog check confirmed absence. No automatic retry ran and no index speedup is claimed. A subsequent aggregate events-lock sample returned no rows; it cannot identify the earlier blocker. Receipts are retained under `rust/target/parity-evidence/release-0836/deploy-plan/`.

After independent review of the sole lock-ceiling change to 10 seconds and separate coordinator authorization, one fresh attempt succeeded. It first confirmed absence; its resource gate passed at load 8.83, CPU pressure 28.48% and approximately 4.8 GiB available memory. The exact index definition was valid and ready after creation and in a separate independent catalog read. Both attempts and cleanup receipts are retained. No authenticated request timings or end-to-end speedup were measured, and no native migration switch changed.

A nonexecuting production EXPLAIN of the same unchanged alias-denial SQL now uses the new expression index in both the outer normalized-key filter and the correlated original lookup. Estimated total cost changed from 4,781,570.84 in the earlier read-only sample to 13,306.84. These are planner estimates from separate live samples, not executed query timings or a measured browser speedup.
