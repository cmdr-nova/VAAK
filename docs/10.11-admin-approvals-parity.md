# Admin parity and staged registration approvals — 2026-10-11

## Scope and configuration

This document originally described the first, off-by-default Approvals phase. The integrated current contract supersedes its former supplied-invite shortcut: when `VAAK_REGISTRATION_APPROVALS=1`, every public registration submission is an application requiring an administrator decision. A paid Supporter code is optional and never bypasses approval. Pending applications create no account, private key, login session or earned badge; approval creates the account and consumes a valid bound paid reward atomically. Unset/default approval flags retain the legacy required-invite registration behavior. The shared internal `ap_auth_register` compatibility helper is not an alternative public approval-enabled route. Current full FPM tests also deny unapproved account creation through alternate form modes, Mastodon account POST and direct library HTTP entry points. Production activation remains separately gated by the integration plan; this phase does not select beta branding.

Pending records live in `ap_registration_applications`, not `ap_users` or `actor_profile`. They store a password hash, never the plaintext password. Pending applicants cannot satisfy the actual `ap_auth_verify_credentials` lookup used by password login and OAuth authorization (`ap-mastodon.php`). No key generation, operator follow or registration notification runs until an account is approved. The new library refuses direct HTTP access with 403/no-store. The public local actor/account route remains unchanged; absence from the account/profile tables is the capability boundary, not a disabled-account flag.

Admin navigation includes Approvals. Current active admin identity is reread from the database before reads, after reads, and inside decision transactions; callers cannot provide role flags. Existing view/action lists additionally gate the new page and actions. Both decision forms contain session CSRF, and the decision helper independently checks it. The read model excludes password hashes. Results are paged in batches of 100, with previous/next navigation. Applicant email is visible only on this admin page.

## Atomicity and preserved registration behavior

`ap_auth_create_account_row` is a shared internal **transaction-only, no-login** account/profile creation helper. Ordinary invite registration retains its validation, conditional one-use invite update, commit, provisioning, account load and login. Approval uses this helper without calling `ap_auth_register`; the administrator session remains unchanged.

PostgreSQL locks `ap_users` and the applications table in a consistent order. SQLite obtains a write reservation through an UPDATE inside PDO's tracked transaction, even when no row matches. Shared account creation locks the users table and rechecks case-insensitive username/email collisions inside the transaction, serializing invite-versus-approval conflicts. Pending unique indexes prevent duplicate case-insensitive usernames/emails. Approval/rejection conditionally changes only a pending row. Same-decision replays return success without repeating effects; opposite-decision replays fail. Collisions roll back account/profile writes and leave the application pending. Decisions erase the stored applicant hash.

Provisioning occurs after commit, preserving the existing best-effort boundary; keys/follow/notifications are **not transactional delivery**. Both a known unsuccessful actor-key receipt and thrown approval failures at this boundary return an approved result with an operator-attention message rather than falsely reporting the committed account as uncreated. A replay does not retry those effects. The existing provisioning functions remain responsible for key/follow/notification behavior. Invite notification text remains unchanged; approved account notifications accurately say administrator approval. No external notification was sent during verification.

## First independent review and repairs

The first fresh review rejected two P2 defects: a known `ap_actor_ensure_keypair` unsuccessful result was logged but omitted from the approving administrator's outcome, and PHP `password_hash` could throw for an internal NUL before the existing error handler. Both are repaired. The shared provisioning helper now returns its explicit key outcome after the same key/follow/notice order. Approval displays operator attention for the known failure while retaining the committed account and no automatic retry. Invite registration ignores the receipt and retains its prior best-effort behavior. Application and invite hashing catch actual hasher errors and return validation failure before writes; valid-password trim, length policy and hash algorithm are unchanged. The original blocked freeze/control/report remain preserved. Repaired actual SQL checks: 171; concurrent races: 12; real templates/gates: 9. Fresh independent re-review remains required.
