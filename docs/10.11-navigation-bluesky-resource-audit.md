## High-priority database finding

Several concurrently active PostgreSQL queries matched the current Rust audience alias/deletion guard and quote hydration query structures. Their `rtrim(object_id, '/')` equality cannot use the existing raw `object_id` index. The actual production index inventory contains no matching expression index.

Source mapping:

- `rust/vaak-worker/src/audience.rs`: `SELECT DISTINCT rtrim(e.object_id,'/')` checks Delete/Tombstone, deleted Create/Update, and non-public Announce without a matching original Create/Update. The same normalized equality occurs inside its correlated `NOT EXISTS`.
- `rust/vaak-worker/src/home_hydrate_ranked.rs`: cached quote recovery compares normalized object IDs, requires non-deleted Create or public Announce with a matching explicit original actor, and excludes deletion aliases. Self-reply lookup and cached Create lookup also use normalized IDs with latest-ID ordering.
- `api/ap-db.php`: current Bluesky identity expansion resolves an existing handle with `lower(author_handle) = ? AND author_did IS NOT NULL AND author_did <> '' LIMIT 1`. No matching expression index exists on `bsky_posts`.

Non-executing production `EXPLAIN`, using a synthetic nonexistent URI, retained the complete current audience denial predicate. It estimated approximately 184,287 bitmap candidates and total cost 4,727,318, with a correlated full `events` scan and JIT compilation selected. These are planner estimates, **not execution durations**. The simplified Delete/Tombstone predicate also planned approximately 110,000 type-index candidates followed by normalization filtering. The Bluesky handle lookup planned a sequential scan with estimated full-plan cost 40,199.62; its LIMIT estimate was 47.57.

The first proposal is an index supporting normalized event IDs and latest-ID lookup. It retains every audience, deletion, actor-match and visibility predicate. A second proposed index supports the exact Bluesky handle predicate. SQL is reviewable in `10.11-navigation-expression-index-proposal.sql`; it has **not been applied or performance-verified**.

Before applying, independently replay unchanged queries against an isolated representative dataset, covering trailing-slash aliases, deleted/updated originals, private Announce, canonical recovery, mixed-case handles and duplicate handle-to-DID records. The existing handle lookup has no ORDER BY: a new index can change the arbitrary winning row when multiple DIDs share a handle. Resolve/test that ambiguity before describing it as exact parity. Test new plans and result vectors, then compare bounded actual caller latency under comparable load. Do not replace current guards with a cached authorization result or weaken their freshness.

Use an explicit PostgreSQL maintenance step, outside any transaction, rather than `CREATE INDEX CONCURRENTLY` inside the PHP schema bootstrap. Build one index at a time under the observed resource pressure. Inspect `pg_index.indisvalid` and definitions before/after; `IF NOT EXISTS` does not repair a same-name invalid or incorrect index. Plan a bounded lock timeout, verify failure state, and have a concurrent-drop rollback. No new index is authorized for automatic execution by this audit document.

## External Bluesky feed opportunities

All three services retain a 180-second refresh interval; configured candidate caps remain 10,000–12,000 and retention 120–144 hours. Their source hashes and function inventory were observed, not a full transitive-source freeze. No cadence or candidate cap was reduced.

All three `get_skeleton` paths use `ORDER BY CASE WHEN ? THEN like_count ELSE score END DESC, indexed_at DESC`. Read-only SQLite plans show a temporary sort despite an existing `(score DESC, indexed_at DESC)` index. Substituting the selected fixed score expression uses the score index in the observed plans. A later bounded patch could choose between fixed score/like ordering at query construction, preserving images-only filtering, manual allow injections, current block/soft-mode rules, per-author caps, recency boosts, exact candidate window and cursor behavior. Compare tie rows explicitly: changing access paths can change unspecified equal-score/equal-time ordering. This is a proposal, not a demonstrated production CPU reduction.

Each accepted candidate upsert currently opens a SQLite connection and commits separately. Refresh batching/reusing a connection could reduce churn, but must preserve per-post visibility, ordering of duplicate-source updates, failure recovery and concurrent reader behavior. Do not defer all visibility until the refresh completes without testing that behavioral difference. Request-frequency and refresh-cost attribution remain unmeasured: bounded journal sampling provided little feed-generator output, so it cannot establish their request rate. VAAK's five-second Jetstream worker produced zero processed/failed counts in the last five observed runs; that alone does not justify changing its ingestion latency.

## Navigation follow-through

Current soft navigation keeps the latest queued intent while a shell request is busy; notification scrolling already aborts obsolete work and checks that its view remains connected. Preserve these protections. Home helper fetches retain a 1,500 ms budget, so database bursts can plausibly lead to native timeout followed by PHP fallback, but this phase did not pair those events with complete caller requests.

Next bounded optimization gate should measure full navigation, shell fill and Home append separately, recording source/cache/hydration/paint/fallback stages and withdrawal controls. The posting/threading owner is separately fixing own-post fanout sequencing and newer-poll thread refresh/deduplication; this audit did not edit those regions. Avoid broad rendered-page caching or speculative authenticated fetches that retain stale Settings/privacy state. No claims of full navigation performance parity or completed resource optimization are made here.
