# Right sidebar lazy loading — 2026-10-11

This finite change makes the Trending part of the right rail load after document parsing, two paint opportunities and browser idle scheduling on every page. The static Search form performs no background request. On mobile or Blog/DM pages where CSS hides the rail, no Trending request is sent. Visible-again rails schedule a fresh read. Unsupported idle/paint/observer APIs use the same visibility check with a timer fallback.

An unchanged loaded context stays displayed through reply/refresh triggers; identical scheduled or in-flight triggers coalesce. Full document refresh still obtains a new current-policy response, lazily. Context changes remove prior cards and abort the old request. Main navigation starts invalidate the rail; successful direct timeline swaps, full soft-navigation shells and profile shells schedule the correct context after their main content has been installed. Detached older timeline completions cannot change a replacement rail's context. Pending main navigation suppresses background dispatch; there is no navigation timer polling loop.

Privacy remains server-owned: the existing AJAX handler and its current SQL guards, temporary/manual downranking, personal/server blocks/mutes, muted words and nested quote policy are unchanged. Requests remain same-origin, `cache: no-store`, without forcing global candidate collection. No HTML is saved in browser storage. Pagehide/backgrounding remove cards and abort pending work; bfcache/background returns revalidate before repaint. Native privacy/moderation/Settings/account-switch submissions and logout clear existing cards immediately. Native policy submissions do not race a GET using the policy before that POST. Cancelled native submissions safely read current policy again. Failure presents an accessible Retry control without retaining old cards.

## Actual browser evidence

Durable ignored evidence: `rust/target/parity-evidence/sidebar-lazy-phase/`.

- Retained before source: actual loader starts synchronously; two repeated overlapping requests plus hidden Blog, DM and mobile triggers produce **six requests** in the fixture (5 checks).
- Frozen final source: **76** browser checks, including 21 native `requestSubmit()` actions and undo paths, real logout anchor, same-context reply/overlap behavior, hidden rails, resize, lifecycle, stale responses and Retry.
- **6** fallback checks with idle/paint/IntersectionObserver unavailable.
- **12** checks run the actual complete soft-navigation IIFE: main network before background network, latest queued destination, profile and timeline shell completion, authentication denial.
- **9** checks run the actual direct timeline swap function: busy refusal, main-first ordering, success, detached older completion, authentication denial and missing-main return.
- PHP lint passes. Existing `trending-browser-review.py` delegates to the current sidebar harness so its old synchronous-fetch assumptions do not survive as a current gate.

The browser is actual Chromium. The fetch transport records responses; no live server receives requests. Sidebar shell CSS, controlled paint/idle clocks, `document.hidden` overrides and native POST iframe targets are explicit fixture boundaries. The complete soft-navigation controller is real; timeline boot/painter/stream helpers are declared fixture stubs in the narrow tab-function checks. These results establish request ordering/counts and DOM policy lifecycle, **not a measured production latency improvement or live server SQL/load measurement**.

Open-post pages still full-load under the existing route contract. Their sidebar now follows the same lazy scheduler; this change does not migrate post-detail navigation/reply hydration into the soft-navigation controller. No background policy push is introduced: changes from another tab or an administrator while this tab remains continuously visible require the existing context/navigation/background-return revalidation boundary. No claim of real-time cross-tab policy updates is made.

No deployment, commit, native feature-switch activation or registration opening is part of this phase. Independent review is required before publication.
