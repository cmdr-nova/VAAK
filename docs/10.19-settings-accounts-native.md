# Settings account sections native read (step S2, second part)

Rust paints three more sections of the Settings page (`?view=profile`): Pending follower requests, Featured accounts and Muted accounts, with their row forms (approve/reject, move up/down/remove, unmute) and the Featured add form or limit message. PHP keeps the shell, the session, CSRF injection, every action, and every row it would have to fetch, warm or look up before painting.

These are personal sections. Every account can use them, so the worker admits any active account and never checks for admin, the same way as `10.19-settings-lists-native.md`. Rows are always read for the session owner only.

Default off. It needs `VAAK_ADMIN_READ_NATIVE=1` and `VAAK_ADMIN_READ_SECRET` plus `VAAK_SETTINGS_ACCOUNTS_NATIVE=1`, in both `www.conf` and `vaak.env`. It is separate from `VAAK_SETTINGS_LISTS_NATIVE`, so either can be turned off alone.

## What it does

`ap_settings_native_body($view, $viewerAdmin)` posts the usual envelope to `/internal/admin/read` with `view` set to `settings_follow_requests`, `settings_featured` or `settings_mutes`, offset 0 and `viewer_admin`. The worker requires the owner to exist, not be disabled and have exactly that admin role, before and after a READ ONLY transaction.

- Follow requests: `ap_follow_requests` for the owner's actor id with status `pending`, oldest first. No rows paints nothing, as PHP does.
- Featured: `ap_featured_accounts` for the owner by position, up to 40 rows read and 12 shown. Local targets use `actor_profile` and the local avatar rule; remote targets use the cached actor and a cached avatar.
- Muted accounts: `ap_mutes` for the owner, newest first. `ap_mutes_list` now breaks created_at ties by actor id so both sides order same-second rows alike. An uncached or placeholder actor is painted with its fallback label and queued for a warm (Redis lock plus `vaak:queue:ap_actor_warm`), exactly the warm PHP's label helper would queue.

The bridge accepts only the closed row shape per view (follow: `id`, `actor_id`, `username`; featured: `id`, `actor_id`, `acct`, `display_name`, `avatar`; mutes: `actor_id`, `created_at`), checks the request binding including `viewer_admin`, then rechecks that the session user and their admin role are unchanged.

Renders the PHP section instead when: a featured avatar is not cached yet (PHP would fetch it), a local featured account has no profile row, a muted account's avatar is missing or unsafe, a muted account's name has custom emoji, a muted actor is local, a created_at the helper can't parse, more than 1000 mutes or follow requests, the account is unknown or disabled, its admin role changed, the session owner differs from the page owner, or anything else in the bridge refuses.

## Parity check

`api/bin/settings-accounts-native-review.php` (sandbox only) renders the genuine three template regions with the genuine PHP helpers (actor fetch, media, emoji and profile calls stubbed to record effects) and compares whitespace-collapsed HTML for an admin and an ordinary account, in full and shell modes. A third account's rows are seeded in every case and must never appear. It checks PHP made no fetch or emoji effects for painted rows, that PHP's actor warms equal the native queue entries, and that the real bridge validator accepts each reply and rejects an extra row key and a flipped role binding. Fallbacks: every case listed above, plus missing role and nonzero offset.
