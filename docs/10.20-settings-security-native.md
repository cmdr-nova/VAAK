# Settings Security page native read (step S5)

Rust paints two sections of the Security page (`?view=security`): the two-factor card when 2FA is enabled or not yet set up, and "Your OAuth tokens" with the operator purge button and one card per token (app name, id, scopes, created, expires, revoked, status, and the Revoke form for active tokens). PHP keeps the shell, the session, the account header, the password forms, browser notifications, the operator app password card, every action (`2fa_begin_setup`, `2fa_confirm_setup`, `2fa_disable`, `revoke_oauth_token`, `purge_oauth_tokens`) and CSRF.

No secret is read. The token query selects only `id`, `scopes`, `created_at`, `expires_at`, `revoked_at` and the app's `client_name`: never `access_token_hash`, `refresh_token_hash` or `client_secret_hash`. The 2FA query returns one boolean, `trim(secret_enc) <> '' AND trim(enabled_at) <> ''`, and never selects `secret_enc`, `pending_secret_enc` or `recovery_codes_json`. Rows are `{id, status}` per token and `{panel: "two_factor", enabled: bool}`. The page is open to every active account, never admin-gated. The purge button keeps PHP's rule: actor key `cmdr_nova` (a NULL actor key reads as `cmdr_nova`, as on the page) and an admin session.

The 2FA setup step (the Base32 key and QR) and the one-time recovery codes stay PHP. Both come from the session or the request that just created them, not from a read, and they are secrets the worker should never see.

Default off. It needs `VAAK_ADMIN_READ_NATIVE=1` and `VAAK_ADMIN_READ_SECRET` plus `VAAK_SETTINGS_SECURITY_NATIVE=1`, in both `www.conf` and `vaak.env`. One flag covers both views.

## What it does

`ap_settings_native_body('settings_two_factor' | 'settings_tokens', $viewerAdmin)` posts the usual envelope with offset 0 and `viewer_admin`. The worker requires the owner to exist, not be disabled and have exactly that admin role, before and after a READ ONLY transaction.

Tokens copy `ap_oauth_tokens_list(40, 7, $owner)`: revoked rows older than seven days are left out (cutoff `gmdate('c')` compared as text, as PHP binds it), the newest 40 by id, and the `cmdr_nova` user (else user 1, as `ap_db_cmdr_nova_user_id`) also sees legacy rows with a NULL `user_id`. A token is revoked when `revoked_at` is non-empty, else expired when `expires_at` parses to a time before the request's `now`, else active. The template's PHP token query now runs only in the fallback branch, so a native render does not query the tokens twice.

The 2FA wrapper sits after the recovery-code and setup branches, so those states always render in PHP.

Renders the PHP section instead when: an `expires_at` is not `gmdate('c')` or offset-bearing Postgres text (PHP's `strtotime` would read a zoneless or relative date by its own rules), printed text matches the `ap_fix_utf8` mojibake pattern that `h()` would repair, a table is missing (PHP shows 2FA as off), the account is unknown or disabled, its admin role changed, the session owner differs from the page owner, or anything else in the bridge refuses.

## Parity check

`api/bin/settings-security-native-review.php` (sandbox only) renders the genuine template branches with the genuine `ap_oauth_tokens_list`, `ap_db_cmdr_nova_user_id` (static cache removed), `ap_auth_2fa_row`, `ap_auth_2fa_enabled` and `h`, and compares whitespace-collapsed HTML in full and shell modes for: the operator with active, expired, recently revoked, long-revoked (hidden), legacy NULL-owner, unknown-app, missing-expiry, empty-expiry and Postgres-format tokens; an ordinary account; a NULL actor key that is not the operator; an account with no tokens; and a second admin who gets no purge button. 2FA covers enabled, no row, pending setup, whitespace-only secret and whitespace-only `enabled_at`. It also checks the purge count, revoke forms, escaped app names and CSRF, no cmdr_nova row (legacy rows go to user 1, no purge), a NULL actor key admin (purge shown), and the 40-row cap. Every token hash, refresh hash, client secret, TOTP secret, pending secret and recovery code is a decoy that must never appear in a reply. The real bridge validator must accept each reply and reject an unknown status, a string id, an extra row key, a non-boolean 2FA state, another panel, two 2FA rows and a flipped role binding. Fallbacks: every case listed above, plus missing role and nonzero offset.
