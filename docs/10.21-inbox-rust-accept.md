# Rust inbox front door (cutover F2)

Default off. F1 (`VAAK_INBOX_SIG_SHADOW`) showed Rust and PHP reaching the same signature verdict on 43,659 real deliveries with no disagreement. F2 lets Rust answer the common delivery itself.

## What Rust accepts

`vaak-worker serve` handles `POST /inbox`, `/inbox/`, `/users/{key}/inbox` and `/users/{key}/inbox/`. It spools a delivery and answers `202 {"status":"accepted","action":"spooled"}` only when all of these hold:

- the switch is on and the body is 1 byte to 256 KiB
- PHP has verified a delivery with this keyId in the last 24 hours, so the key is mirrored in cache Redis (`vaak:inbox:key:v1:{sha256(keyId)}`, `AP_INBOX_RUST_KEY_MIRROR_TTL`). A rotated key fails here and goes to PHP, which fetches and mirrors the new one. Keys of accepted relays are mirrored with `relay: true`
- the client IP is within PHP's per-hour limits (Redis counters; PHP keeps its own): 600 for normal senders, and for a relay key 12,000 in its own bucket while the IP's normal bucket is not spent
- the signature verifies with the F1 verifier (draft-cavage or RFC 9421)
- the keyId host is not under a domain block
- the body is JSON with a string `type` and an https `actor`. A signer who is not the actor is spooled too (stat `spooled_mismatch`, except a relay's Create or Announce, which counts as `spooled`), and the drain decides; those rows skip the duplicate check, since a signer can claim any activity id
- for `/users/{name}/inbox`, `name` is an active local user (otherwise `ap-user.php` answers 404, so the request goes to PHP)

Anything else is forwarded unchanged (method, path, query, headers including Host and X-Forwarded-For, body) to `VAAK_INBOX_PHP_URL` (default `http://127.0.0.1:8796`), and PHP's answer goes back to the sender. Unknown keys, bad signatures, blocks and the other rejections stay PHP's. If PHP cannot be reached the worker answers 503 with `Retry-After: 60`, so senders retry.

## Fetching unknown keys

With `VAAK_INBOX_RUST_KEY_FETCH=1` in `/etc/mkultra/vaak.env` (worker only), a shared-inbox delivery whose key is not mirrored no longer goes straight to PHP. The worker first charges the IP's normal rate bucket and checks domain blocks, then does what `ap_fetch_actor_pubkey` does (`rust/vaak-worker/src/inbox_key_fetch.rs`):

- skips keys in the negative cache, now shared through cache Redis (`vaak:inbox:keyneg:v1:{sha256(keyId)}`, 15 minutes; PHP's `ap_key_neg_cache_*` read and write it next to their /tmp files)
- spends the same fetch budgets (`vaak:rate:` counters, 6 per key and 240 per host each 10 minutes)
- tries the same candidate URLs, connecting only to addresses that all pass the public-address check, with no redirects, an 8 second timeout and a 256 KiB cap
- signs the GET as cmdr_nova exactly like `ap_signed_get_ex` (`rust/vaak-worker/src/ap_sign.rs`; parity case `ap-sign` checks the bytes). The key is read from `VAAK_AP_SIGNING_KEY` (default `/etc/mkultra/ap-inbox/cmdr_nova_private.pem`, readable by www-data like PHP) with keyId `VAAK_AP_SIGNING_KEY_ID`
- on success writes the key mirror (with owner and relay flag) and carries on as for a mirrored key; on failure records the negative cache entry and forwards to PHP, which then skips its own fetch

Personal inbox paths keep going to PHP, because PHP signs their key fetch as that user. Stats: `key_fetched`, and `fwd_key_negative`, `fwd_key_budget`, `fwd_key_not_public`, `fwd_key_fetch_failed` for the misses.

## Processing

Spooled rows land in `ap_inbox_spool` (migration `20261029_inbox_spool_postgres.sql`). `api/bin/inbox-spool-drain.php` claims one row at a time (`FOR UPDATE SKIP LOCKED`), sets the request actor from the path the way `ap_inbox_main` does, re-checks the block list and actor/key match, then calls `ap_route_verified_activity`. For a signer who is not the actor it does what `ap_inbox_main` does: a Create or Announce forwarded by an accepted relay or a followed account is taken (a forwarded Create is replaced by the copy its author's server serves, `ap_inbox_refetch_forwarded_create`, or dropped as `forward_dropped`); anything else is replaced by the actor's own copy (`ap_inbox_recover_unverified`) or dropped as `actor_mismatch`. PHP answered those last ones 401; the spool answered 202 before deciding. Errors retry with backoff up to 5 attempts, then the row stays `failed` for review. A routing rejection (a block found while routing) marks the row `dropped`. Rows stuck in `processing` for 10 minutes go back to `pending`, or to `failed` once they have used their 5 attempts. Done and dropped rows are deleted after 7 days.

The drain copies the PHP-FPM pool's `env[]` lines (`VAAK_FPM_POOL_CONF`, default `/etc/php/8.3/fpm/pool.d/www.conf`) so routing sees the same flags as the inbox did. It exits after `--budget` seconds (300 in the unit) and systemd restarts it.

## Turning it on

1. Deploy a release with this change, so the migration runs.
2. Install the drain unit as root: copy `deploy/vaak-inbox-spool-drain.service` to `/etc/systemd/system/`, then `systemctl daemon-reload && systemctl enable --now vaak-inbox-spool-drain`.
3. Add `VAAK_INBOX_RUST_ACCEPT=1` to `www.conf` (PHP mirrors keys) and `/etc/mkultra/vaak.env` (worker). Reload php8.3-fpm and restart vaak-worker-shadow-http.
4. Caddy, with the current inbox block as the model:
   - a loopback-only site for the PHP fallback that serves exactly what the public inbox route serves today (same root and `php_fastcgi`; `/inbox` rewrites to `/api/ap-inbox.php` and `/users/*/inbox` to `ap-user.php`, as on the public site), bound to `127.0.0.1:8796`, with `trusted_proxies static 127.0.0.1/32` for that server so PHP still sees the sender's address
   - on the public site, a matcher for `POST` on the four inbox paths that `reverse_proxy 127.0.0.1:8787` (the `vaak-worker-shadow-http` bind), placed before the existing inbox handling. Only these POST paths reach the worker this way
   - `caddy validate`, then `systemctl reload caddy`
5. Watch `HGETALL vaak:inbox_rust:stats:v1` (cache Redis): `spooled` versus each `fwd_*` reason. `SELECT state, count(*) FROM ap_inbox_spool GROUP BY 1` shows the drain keeping up.

Keys reach Redis only as PHP verifies deliveries, so `fwd_no_key` is high right after turning it on and falls as senders come back.

## Routing Deletes: shadow (cutover F3)

Default off. With `VAAK_INBOX_ROUTE_SHADOW=1` in `/etc/mkultra/vaak.env` (worker only), a `Delete` or `Tombstone` the worker spools from a signer who is the actor also gets the result Rust predicts `ap_route_verified_activity` will return, written in the same statement as the spool row to `ap_inbox_route_shadow` (migration `20261104_inbox_route_shadow_postgres.sql`). Rust changes nothing else; the drain still routes every row.

`rust/vaak-worker/src/inbox_route_shadow.rs` mirrors the Delete branch: the ids are the object id, a Tombstone's own id and a nested object's `id` (else `object`), each kept only when its host is the actor's host and not ours (`ap_inbox_object_owned_by_actor`). A matching timeline event (`ap_events_mark_object_deleted`'s conditions) predicts `local_status_delete`, else a live mention (`ap_mention_soft_delete`, including `id#…` rows) `local_mention_delete`, else `delete_noop`. A lookup that fails or takes over 400 ms leaves the row without a prediction.

After routing a Delete/Tombstone, `api/bin/inbox-spool-drain.php` compares: `HGETALL vaak:inbox_route_shadow:stats:v1` (cache Redis) counts `agree`, `disagree` and `skipped` (PHP ended outside the Delete branch, such as a block found while routing), each also split by the Rust prediction (`agree:delete_noop`, …). A disagreement logs `route_shadow_disagree id=… rust=… php=…` in ap-inbox.log, and the row's `ap_inbox_spool` id finds the body. The drain deletes shadow rows after 7 days.

- On: deploy (the migration runs), add `VAAK_INBOX_ROUTE_SHADOW=1`, restart vaak-worker-shadow-http.
- Off: remove it and restart.
- Next (F3 switch): once a day of Deletes shows no disagreement, Rust applies them itself (soft-deletes plus the notification, unread, search and DM invalidations PHP does).

## Rollback

Remove the Caddy matcher and reload Caddy: PHP takes every request again. Keep the drain running until `pending` is 0, then stop it if wanted. Turning off `VAAK_INBOX_RUST_ACCEPT` in `vaak.env` alone also works: the worker then forwards everything.
