# VAAK Rust parity audit — 2026-10-10

Audited checkout/release **0.8.32**, commit `c934f0627cf4eaf48c0661fc25096df83b6760e8`, and read-only production state on `144.91.124.35`. This is an implementation/ownership audit, not certification that every UI, remote-protocol, pagination, error, or concurrency case matches PHP.

PHP remains a primary implementation across much of VAAK. Rust is primary for the hot timeline/notification reads and several cache workers. An available Rust projection, a Rust-served PHP HTML cache, and a complete native replacement are different levels of coverage. Absence of a Rust replacement does not imply the PHP feature is broken.

## Cross-cutting systems still dependent on PHP or another runtime

1. **Authentication and public API boundary:** sessions, CSRF, OAuth/apps/tokens, registration, account roles and authorization. Axum is loopback/internal; its owner IDs are supplied by the PHP boundary. Promoting it to a public server requires equivalent identity and authorization behavior.
2. **Mastodon-compatible API:** most public account, status/detail/context, media, lists, searches, polls, filters, markers, relationship and write endpoints remain PHP. Axum's public-shaped endpoints chiefly cover Home and notification reads; grouped notifications and surrounding API behavior remain PHP-owned.
3. **ActivityPub:** inbox/outbox handling, HTTP signatures, actor and note documents, WebFinger/NodeInfo/host metadata, publish/fan-out delivery, follow/undo/like/announce/delete/update and quote authorization remain PHP. Rust's AP actor-warm loop explicitly spawns PHP for signed AS2 fetching.
4. **User action execution:** publishing, replies/quotes, favourites, boosts, bookmarks, follows, mute/block changes, polls, edits/deletes/pins and durable retries. Rust action-queue is an inspector; PHP claims and executes those jobs.
5. **Notification ingestion/delivery:** projection generation and cold fills, Bluesky notification polling, incoming federation/Webmention/Ask notifications and web push. Rust badge/list readers do not replace those producers.
6. **Bluesky/ATProto:** connection/credential refresh, cross-post writes and retries, polling/follow/mod-list sync and PDS management. Jetstream collector is Python, ingest/wanted-DID jobs are PHP; Rust Jetstream module is a read-only scanner. Rust actor and thin-post warming are native and should not be mislabeled wholly missing.
7. **RSS/blog/site publishing:** subscription poller, feed fetch/parsing, blog mutations/export and scheduled publication remain PHP-led.
8. **Media:** upload/R2 storage, user media operations, remote media download/cleanup and object deletion remain PHP-led. Rust Bluesky thin-media warming and status media rendering cover only part of the pipeline.
9. **Link/quote preview production:** Rust attaches cached link cards; PHP owns remote preview fetch/warm jobs and important remote quote target resolution. Rust card display is not complete fetch-worker parity.
10. **Retention/account deletion:** maintenance scheduling, seven-day post deletion, archive/delete workflow, account deletion and R2 delete execution are PHP. Rust cleanup contains matching decision helpers and explicitly refuses execution.
11. **OpenSim operations:** Rust has guarded bridge support; PHP sync/decay jobs and hub remain. The external OpenSim service is a separate system, not a PHP fallback to replace blindly.
12. **Operations:** backup/integrity/service scripts include shell/Python/PHP by design. A literal all-Rust operations stack is a separate objective from feature parity.

## Production checks and evidence

- Nine `vaak-worker-*` services were running, alongside `vaak-redis-queue-worker` and two Jetstream collector instances.
- Ten read-only Axum probes returned **200**: You/drafts, relationships, Settings, integrations, private-surface policy, Search results, Library/bookmarks, Phyrian, admin health and action queue. Availability proves those implementations exist; it does not establish browser integration or full parity.
- PHP-FPM pool config explicitly enables `VAAK_PHYRIAN_RUST_MUTATIONS=1`. Phyrian must therefore be classified as **partial native writes with PHP boundary/fallback**, not simply “PHP writes only” or “disabled by default.” The bridge was not mutated during this audit.
- Active non-comment cron entries reference 17 PHP job paths: actions, actor refresh, Bluesky cross-post retry/notification polling/timeline warming, defederation monitor, delivery sweep/fan-out/publish, maintenance, three media warm/cleanup jobs, scheduled publication, RSS polling and Phyrian sync/decay. This verifies scheduling references, not successful execution of every job.
- `/shadow/private-surfaces` explicitly returns a content-free contract. `/shadow/action-queue` explicitly states it only lists jobs. `/shadow/settings` reports `mutation_enabled=false`.
- No production preferences, messages, posts, relationships or queue jobs were modified. No deployment is needed for this audit.

## Suggested migration order

1. Finish and compare **Library native card rendering**, **Search page integration/remote resolution**, **remote profile/status detail**, and the missing **Lists/Collections/Hashtags/For You/Discuss** read controllers.
2. Complete **You/Settings/administrative read rendering** while preserving the existing authenticated shell; prove filters, pagination, account isolation, errors and stale/cold behavior.
3. Finish the **Phyrian/OpenSim integration and sync/decay gates** separately; its existing native writes need transaction and actual remote-state verification.
4. Migrate **background ingestion/preview/actor/action/delivery workers** individually with lease/retry/idempotency and recovery parity.
5. Move **auth, federation and privacy-sensitive user writes** only after explicit behavior, authorization/CSRF, protocol and rollback gates.

A 100% parity claim requires per-feature comparisons of success/error responses, ownership/privacy, persistence side effects, pagination/filtering, cold/stale paths, retries/idempotency, external failures and browser/API clients. Existing tests are valuable but do not certify that whole matrix. No honest percentage can be inferred from module counts.
