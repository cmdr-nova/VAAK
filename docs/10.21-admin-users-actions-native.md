# Admin user ban and unban native (step A10d)

The worker runs `user_ban` and `user_unban` from the Users page. PHP keeps the session, CSRF, the admin-only gate, the notice and error text, and the page. It uses the `/internal/admin/action` route, bridge and reply from A10a (`10.21-admin-downranking-actions-native.md`).

Admin only. Default off. It needs `VAAK_ADMIN_READ_NATIVE=1` and `VAAK_ADMIN_READ_SECRET` plus `VAAK_ADMIN_USERS_ACTIONS_NATIVE=1`, in both `www.conf` and `vaak.env`. Other families' switches do not open this one.

## What it does

Copied from `ap_auth_user_set_disabled`, inside a transaction that first reads the acting account `FOR SHARE` (an active admin with the actor key PHP sent):

- an id below 1 answers "Invalid user.", a missing account "User not found.";
- the target row is read `FOR UPDATE`, so its role cannot change between the check and the write; the `cmdr_nova` key or any admin answers "The operator account cannot be banned here.";
- ban sets `disabled_at` and `updated_at` and revokes every unrevoked OAuth token of that account; unban clears `disabled_at`. Both run in the one transaction, so a ban never lands without its token revocation (PHP runs them as two separate statements).

Outcomes: `banned`, `unbanned`, `invalid_user`, `user_not_found`, `protected_user`. Nothing about accounts is cached in Redis, so there is no after-save work.

Runs in PHP instead (the worker answers 422 before any write) when a user id is past int4 on an INTEGER table (PHP's query raises), the acting account is not an active admin with that actor key, or any query fails.

## Parity check

`api/bin/admin-users-actions-native-review.php` (sandbox only) runs the genuine handler from `ap-admin.php` with the genuine `ap_auth_user_set_disabled` against a seeded PostgreSQL fixture. For each scenario it runs PHP with the switch off, reseeds, runs the native branch with PHP's handler disabled, and compares the notice, error, view, every account row and every OAuth token row. It also checks the fallbacks write nothing (including a ban that rolls back when the token update fails) and the bridge validator. Run the worker with `VAAK_ADMIN_USERS_ACTIONS_NATIVE=1`.

Scenarios cover banning an ordinary account (one live token revoked, one already revoked left alone, other accounts' tokens untouched), an account with a NULL admin flag, an already banned account, unbanning a banned and an active account, the operator, another admin, a disabled admin, a non-admin row with the `cmdr_nova` key, missing, zero and junk ids, and a ban made by a second admin.

2026-10-21: 52/52 checks with INTEGER ids and 53/53 with BIGINT ids.
