# Settings PostgreSQL / native read gate — 2026-10-11

The bounded persisted Settings read gate passes **3,628 assertions and 82 paired captures** against the actual Rust `/shadow/settings` HTTP endpoint and genuine PHP `ap_profile_save`, `ap_profile_save_unlocked`, and `ap_profile_get` declarations. No Settings runtime changes were needed for this gate. This does **not** certify a native Settings editor, all Settings controllers, or 100% Library/Search/remote-profile parity. The earlier 343-assertion SQLite behavior corpus remains narrower evidence and does not certify a full native Settings renderer.

## Independent evidence

`api/bin/settings-postgres-native-reference.php` creates and drops unique disposable PostgreSQL schemas. User IDs use the production pgloader `BIGINT` type; the entire corpus runs separately with `INTEGER` and `BIGINT` preference columns. The profile schema preserves production relevant field types, NOT NULL constraints, and preference defaults. Initial disabled preferences are explicit seeded inputs, rather than altered schema defaults.

The runner loads 17 unchanged PHP declarations with the token-based source extractor. It never includes production configuration or runs the application's database migration/bootstrap. Real mbstring and PDO PostgreSQL extensions are required. It starts the actual freshly built Rust worker, with nonexistent environment-file paths, isolated database search paths, native migration flags off, and unused external endpoints directed to loopback port 1. The worker's actual settings code performs its real current SQL query. No copied query, substitute Rust decision, or expected-output rewriting supplies the response.

The recorded substitutions are transport boundaries: `ap_db` connects to the disposable schema; Redis get/set/delete use a request-local in-memory cache; timeline invalidation calls record their owner IDs. Genuine attachment verification executes on non-URL attachment text, so it makes no remote request. Genuine public-profile export executes for fixture actor keys and takes its existing non-`cmdr_nova` early return. No exported files or federation messages are produced.

Each paired capture retains the persisted profile row, actual PHP read, actual native HTTP status/body, and cache effects. Artifact: `/tmp/vaak-settings-postgres-native-reference.json`. It includes the captured schema column types/defaults/nullability, all 17 individual helper-body hashes, complete production source hashes, the exact 26-key canonical contract, and the actual tested worker binary hash. Both worker processes terminate and both schemas drop in `finally`; the shared disposable PostgreSQL container remains running.

## Covered behavior

- Every one of the 16 canonical boolean preferences is enabled and disabled through the genuine PHP save. Actual native boolean reads agree with the PHP read. Each partial enable preserves every omitted preference and the other account's complete native projection.
- Reply and quote policy values `anyone`, `followers`, and `nobody` are saved and read. A locked-account baseline retains manual approval, directory/indexing opt-outs, collection-consent opt-out, and restrictive interaction policies through independent partial writers.
- Name, sanitized summary, signature, nullable media fields, attachment JSON, badge JSON, and update timestamp agree with the persisted/PHP values. Unicode text is retained; valid badges and rejection of an unknown badge execute genuine normalization.
- Only actual algorithm transitions invalidate the current owner's ranked/hydrated caches. The other owner remains unchanged.
- Two separate PHP writer processes visibly queue on the real per-actor PostgreSQL advisory lock before release. `pg_stat_activity` observed **two advisory lock waiters for each column width**. Both partial saves survive; omitted privacy preferences and policies survive. This is stronger than starting two processes and hoping they overlap.
- A genuine PHP save inside an open PostgreSQL transaction remains invisible to a separate Rust HTTP connection. Rollback restores the exact canonical native fields. A rejected invalid-name save leaves all fields unchanged.
- Missing users, missing joined profiles, and disabled users produce the actual native error response. Changing the current persisted user actor key/profile identity changes the projection immediately.
- Every successful projection has exactly the 26 canonical `CANONICAL_FIELDS` keys, checked against the Rust constant and its existing contract fixture. Secret fields are absent; a declared test-only private sentinel in an extra profile SQL column is never exported. POST to the Settings route returns 405 and changes nothing; successful replies declare PHP mutation ownership and `mutation_enabled=false`.
- An actual worker invocation refuses a non-loopback listener. The existing internal query behavior is retained: omitted, zero, or negative owner IDs resolve to the configured default; malformed integer query values return Axum's 400 text response. That default-owner behavior is an internal API convention, not evidence of authenticated public user authorization.

## Reproduction

Build a fresh worker with `LD_LIBRARY_PATH=/usr/lib/rustlib/x86_64-unknown-linux-gnu/lib cargo build --manifest-path rust/Cargo.toml --bin vaak-worker --offline`. Then:

```bash
LIBRARY_FIXTURE_SOCKET=/tmp/vaak-library-facts-pg-socket \
  api/bin/php-policy-test \
  -d extension=/tmp/vaak-php-pgsql-test/extracted/usr/lib/php/20230831/pdo_pgsql.so \
  api/bin/settings-postgres-native-reference.php
```

The disposable PostgreSQL socket and loopback listeners need sandbox escalation when the sandbox reports EPERM. The initial run hit that restriction; the isolated rerun was approved. PHP syntax and `git diff --check` pass.

## Remaining scope

The current Rust surface is a persisted profile/preference projection, not a native mutation path. PHP remains responsible for authentication, CSRF, profile writes, uploads, passwords/2FA, account links, integrations, imports, export/federation effects, and their controllers. This gate does not test those full browser/controller flows, Redis deployment behavior, real remote rel=me verification, public-page consent enforcement, a production bootstrap, or arbitrary corrupt/legacy profile rows. Settings preferences still require the separate Library/Search/remote-profile admission and rendering gates to prove their downstream behavior. No flags were activated and no commit, deployment, or production write occurred.
