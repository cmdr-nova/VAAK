# Search native collector (cutover step 12)

`admin_search_run` (full Search page, soft-nav shell and the scroll fragment)
can ask the Rust worker to collect the result window instead of PHP. The
worker returns the same bundle PHP builds: accounts, hashtags, statuses,
`has_more`, and the private `_native_collector` / `_native_components`
descriptors the existing render bridge binds. It writes the same short cache
file (`s_<sha256>.json` under `/var/lib/mkultra/ap/search-cache`), so later
pages and tag clicks reuse it whichever side served the first page.

Default off. Nothing changes until the switch below is set.

## What runs natively

- Ranked status window: the shared FTS ranking (`search_ranked.rs`), the same
  hydration and Announce-to-Create remap, the profile/Library status builders
  for local and federated rows, a Bluesky builder for `bsky_post` hits, the
  30-day Bluesky LIKE fill, and the sanitizer. Building stops as soon as the
  40 kept statuses exist, which keeps the same window and skips the rest of
  the builder IO.
- Current admission (hidden, indexable, audience) and downranking: downranked
  posts move below the rest, as on Home (PR #60).
- Hashtag counts over the same 400/600/300 row windows, with follow state.
- Accounts: local handles, our-host and typo forms, local user listing, and
  the cached `remote_actors` name search.
- Pasted post URLs still return the empty window, as before.
- Pasted post URL redirect: `/internal/search/resolve` looks the URL up in
  stored rows only (events by object id, then `masto_statuses.note_id`). On a
  miss the worker answers 422 and PHP does the network fetch as before, with
  the existing SSRF guards. The block check stays in PHP either way.

## What stays on PHP (whole request)

The worker answers 422 and PHP collects as before when it meets:

- a mention hit that is a Bluesky mention, an Ask, a quote, or carries keyed
  media or a Bluesky reply target (fediverse mentions run natively since
  step 13);
- an Ask or quote body that PHP rewrites;
- the search index still backfilling, or the newest event not indexed yet
  (PHP's search-time indexer runs first);
- anything unexpected (logged at info as `Search collect PHP fallback` with
  the reason).

## What stays on PHP (account section only)

Remote host listings (`example.social`), `@user@host` with Resolve remote
(WebFinger), and bridged Bluesky accounts. The worker returns everything else
and PHP fills only the account section, so statuses are never collected twice.

## Step 13 additions (same switch)

Everything below rides `VAAK_SEARCH_NATIVE_COLLECT=1`; with it off nothing
changes.

- **Thin Bluesky authors.** The worker now does what PHP's
  `ap_bsky_actor_refresh_enqueue` does: an upsert into
  `bsky_actor_refresh_queue` (skipped when the cached profile has a viewer row
  and is under 6 h old) and, when `VAAK_ACTOR_WARM_RUST_PRIMARY` is on (the
  default), the same `bsky_actor_warm` Redis push on the queue database. The
  profile cache read is a full port of `ap_bsky_actor_profile_cache_get`, so
  the `vaak:profile:v1:bsky:*` Redis keys are shared with PHP.
- **Mention hits.** Fediverse mentions are built natively (port of
  `ap_masto_status_from_mention`, `ap_masto_clean_mention_text` and the
  status-ref resolver). The cases listed above still fall back.
- **Bridged and Threads accounts on cards.** Search cards now use PHP's web
  URLs for bridged Bluesky, `bsky.app` and Threads authors, the placeholder
  account-id logic, and `ap_remote_object_web_url` for the status `url`. This
  is limited to Search; profile pages and Library keep their current
  behaviour (they still hand those authors to PHP).
- **Connection reuse.** Collect, resolve and the Search render reuse up to two
  idle Postgres connections instead of opening a new one per request (about
  2 ms each on a local pgbench, more under load). No new pool, thread or timer;
  a connection that errored is dropped, not returned. The render only reuses
  when the switch is on.

Still on PHP after step 13, on purpose:

- Bluesky mentions (they need AppView media hydration) and Ask/quote bodies.
- Remote host listings, WebFinger and Bluesky handle resolution, and pasted
  URLs that need a network fetch (those depend on the PR #68 SSRF guards, which
  stay in PHP).
- Follow state for a `bsky.app/profile/<handle>` result that is not resolved
  to a DID yet (the render hands it to PHP, which resolves the handle).
- Index writing (PHP still indexes on insert).
- Collect and render stay two calls: render needs PHP's preview budget and
  session state, and merging them saves one local hop for a lot of risk.

## Card build speedup (always on)

The shared status builders compiled their regexes on every call, about 85 ms
per card even in a release build. They now compile each pattern once
(`re!` / `cached_re` in `profile_materialize.rs`). This is not behind the
flag, and it also speeds up the native profile pages already serving.

## Switch on

1. In the PHP-FPM pool (`www.conf`) and the worker env (`vaak.env`), add
   `VAAK_SEARCH_NATIVE_COLLECT=1`. `VAAK_SEARCH_NATIVE_SECRET` is already
   shared with the render bridge; both sides need the same value (32+ chars).
2. Back up both files first (`.bak-search-collect-<timestamp>`).
3. Restart the worker, then reload PHP-FPM.

Optional: `VAAK_SEARCH_NATIVE_COLLECT_URL` overrides the loopback URL
(default `http://127.0.0.1:8787/internal/search/collect`; only loopback http
is accepted). The resolve call uses the same host with `/internal/search/resolve`.

## Rollback

Restore `www.conf` and `vaak.env` from the `.bak-search-collect-*` copies (or
delete the `VAAK_SEARCH_NATIVE_COLLECT=1` lines), restart the worker, reload
PHP-FPM. With the switch off the route is not registered and PHP never calls
it. Cache files are interchangeable, so no cleanup is needed.
Step 13 rolls back the same way; there is no separate switch.

## Verification

`php oracle.php` (PHP) and the ignored `search_collect::oracle::php_oracle_dump`
test (Rust) run the same cases on two copies of one seeded fixture database;
bundles, cache contents and side-effect rows (`masto_account_actors`,
`remote_post_media_cache`) compared equal for all 18 cases, including tag,
offset/cache-read, downrank, mute, non-indexable, local, typo and
account-fallback cases. The cache file bytes differ (key order), which is
fine: the render bridge checks the sha of the file it reads.
